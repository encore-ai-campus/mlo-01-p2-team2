# 내부 인사 요청 검토 가이드 UAT 체크리스트

각 항목을 `PASS`, `FAIL`, `BLOCKED`로 기록한다. P0 항목이 모두 `PASS`여야 Gate 2를 승인할 수 있다.

## P0 범위와 문구

- [ ] 모든 화면에 현재 등록정보 기준과 HR 최종 판단 원칙이 표시된다.
- [ ] 자동선정·자동 승인·자동 반려·채용결정 기능과 버튼이 없다.
- [ ] `현재 데이터상 검토 대상 없음`이 신규채용 필요를 뜻하지 않음을 HR과 팀 관리자가 동일하게 이해한다.
- [ ] `내부 검토 대상 있음`이 인사 요청의 부당함을 뜻하지 않음을 HR과 팀 관리자가 동일하게 이해한다.

## P0 팀 관리자

- [ ] HTML과 네트워크 응답에 후보 이름·ID·부서·직위·근속·개별 경고가 없다.
- [ ] 업무영역·현재값 확인 대상 수·상태·보류 표시가 기준 SQL과 일치한다.
- [ ] 기존 인사요청 또는 SSO 조직정보로 승인된 요청 대상만 조회할 수 있다.
- [ ] 임의 ID 반복 입력으로 직원 존재·재직/퇴직 상태를 알아낼 수 없다.

현재 마지막 두 항목은 요청 소유권 정본이 없어 `BLOCKED`다.

## P0 HR

- [ ] 현재값 확인 대상의 이름·부서·직위·근속·부서/직위 일치 근거가 정확하다.
- [ ] 데이터 확인 필요 대상은 HR에게만 이름·확인 가능한 현재값·경고 이유가 보인다.
- [ ] 데이터 확인 필요 대상은 현재값 확인 대상 수에서 제외된다.
- [ ] 같은 관리자 ID가 여러 AREA에 있어도 같은 Parent 안에서 중복 집계되지 않는다.
- [ ] 여러 Parent에 같은 후보가 나타날 때 업무영역별 표시와 전체 고유인원 수가 구분된다.
- [ ] 표시 순서를 인사결정 우선순서로 오인하지 않는다.

## P0 상태와 데이터

- [ ] 정상 0명은 `NO_MATCH/0명`, 누락·충돌은 `ON_HOLD/—`로 구분된다.
- [ ] 비재직 후보와 퇴직 대상 본인은 후보로 노출되지 않는다.
- [ ] 대상 프로필 빈 값, `DATE_CONFLICT`, AREA–PARENT 누락 fixture가 모두 보류된다.
- [ ] 실사용 canonical 데이터가 적재되어 `check_hr_guide_data --strict`가 성공한다.
- [ ] `MINIMUM_READY`가 Gate 1 승인으로 오인되지 않으며 데이터오너가 별도 승인한다.
- [ ] 기준 SQL과 서비스 결과의 표본·집계 대사가 100% 일치한다.

## P0 개인정보와 운영

- [ ] 관리자 ID가 결과 URL, referrer, 앱 로그에 남지 않는다.
- [ ] 검토 응답에 `Cache-Control: no-store`와 `Referrer-Policy: no-referrer`가 적용된다.
- [ ] 미인증·비권한·타요청 접근이 차단된다.
- [ ] 결과 다운로드·내보내기·별도 의사결정 저장 기능이 없다.
- [ ] 그룹 부여·회수와 퇴직자 계정 회수 절차를 운영자가 재현한다.
- [ ] 개인정보 담당자와 HR 업무오너가 서면 승인한다.

## P1 정책 확인

- [ ] 미래 입사일 후보를 `근속 산정 불가`로 남길지 전체 보류할지 데이터오너가 확정한다.
- [ ] upstream에 새 충돌 코드가 생기면 blocking code 목록과 테스트를 함께 갱신한다.
- [ ] 2만 건 규모 스냅샷에서 응답시간과 후보 목록 크기를 확인하고 필요 시 페이지 처리를 결정한다.
- [ ] 운영 WSGI, static, 로그 보관·회전, 백업·복구 절차를 리허설한다.

- 팀 관리자 요청대상 소유권: `BLOCKED`
- 운영 DB migration: 복사본 `PASS`, 원본 `BLOCKED`
