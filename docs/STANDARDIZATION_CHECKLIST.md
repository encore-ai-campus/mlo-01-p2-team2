# Silver 데이터 표준화 체크리스트

- 프로젝트: 퇴직 관리자 발생 시 대체인력 후보 추천 시스템
- 팀: `mlo-01-p2-team2`
- 현재 범위: Bronze 원본 보존 및 Silver 표준화
- 작성 당시 Gold 상태: 보류(TBD). 후속 단계에서 Gold 데이터 패키지, 규칙 기반 후보 정렬 및 Django 내부 검토 화면을 구현했다.
- 팀 합의 결과 반영 파일: [`config/standardization.yaml`](../config/standardization.yaml)

이 문서는 데이터 표준화를 처음 접하는 팀원이 회의에 참여할 수 있도록 용어, 결정할 내용, 추천 기준을 쉬운 표현으로 정리한 가이드다. 회의에서는 Gold 추천 기능을 제외하고 Silver 데이터까지 논의한다.

## 1. 먼저 용어 통일

- **원천 데이터**: 처음 받은 데이터
- **Bronze**: 원천을 수정하지 않고 그대로 보관하는 공간
- **Silver**: 컬럼명, 코드, 날짜, NULL 등을 정리한 데이터
- **표준화**: 다양하게 표현된 값을 하나의 형식으로 통일하는 작업
- **검증**: 표준화 결과가 정해진 규칙에 맞는지 확인하는 작업
- **Quarantine**: 자동 처리할 수 없는 데이터를 정상 데이터와 분리해 보관하는 공간
- **Gold**: Silver 데이터를 검토 목적에 맞게 가공·제공하는 단계. 이 회의 당시에는 보류였으며 후속 단계에서 규칙 기반 후보 정렬과 검토 화면을 구현했다.

> 이번 회의에서는 표준화 까지만 논의한다.

## 2. 회의 목표

회의가 끝났을 때 다음 사항이 결정돼야 한다.

1. 원천 컬럼을 어떤 표준 컬럼으로 바꿀지
2. NULL을 어떻게 처리할지
3. 직원·업무영역 코드를 어떤 형식으로 통일할지
4. 재직 상태를 어떻게 변환할지
5. 날짜를 어떤 형식으로 저장할지
6. 변환할 수 없는 데이터를 어떻게 처리할지
7. 누가 어떤 파일과 작업을 담당할지

최종 결과물은 팀이 합의한 [`standardization.yaml`](../config/standardization.yaml)이다.

## 3. 컬럼명 논의

원천 컬럼과 Silver 표준 컬럼을 하나씩 확인한다.

| 원천 컬럼 | 표준 컬럼 | 의미 |
|---|---|---|
| `mgr_no` | `employee_id` | 관리자·직원 ID |
| `mgr_nm` | `employee_name` | 직원 이름 |
| `mgr_dept_nm` | `department_name` | 부서명 |
| `mgr_pos_nm` | `position_name` | 직위명 |
| `mgr_hire_dtm` | `hire_datetime` | 입사일시 |
| `mgr_act_yn` | `is_active` | 활성·재직 여부 |
| `area_no` | `area_id` | 업무영역 ID |
| `area_nm` | `area_name` | 업무영역명 |
| `area_reg_dtm` | `area_registered_at` | 업무영역 등록일 |
| `p_area_no` | `parent_area_id` | 상위영역 ID |
| `p_area_nm` | `parent_area_name` | 상위영역명 |
| `top_area_no` | `top_area_id` | 최상위영역 ID |
| `top_area_nm` | `top_area_name` | 최상위영역명 |
| `top_area_lvl` | `top_area_level` | 최상위영역 레벨 |
| `top_area_reg_dtm` | `top_area_registered_at` | 최상위영역 등록일 |

### 팀원끼리 확인할 질문

- `mgr`를 계속 `manager`로 표현할지, 공식 가이드처럼 `employee`로 바꿀지
- 한글 설명이 컬럼의 실제 의미와 맞는지
- 누락된 컬럼이 있는지
- 같은 의미인데 이름만 다른 컬럼이 있는지

추천안은 `mgr_no → employee_id`다. 관리자는 직원 중 하나이므로 향후 일반 직원 데이터로 확장하기 쉽다.

## 4. NULL 처리 논의

먼저 어떤 값을 NULL로 볼지 결정한다.

### 추천 NULL 표현

```text
빈 문자열
공백만 있는 문자열
NULL
None
N/A
NA
-
```

### NULL로 처리하면 안 되는 값

```text
0
N
NO
false
미사용
비활성
```

### 꼭 결정할 질문

- `-`는 항상 NULL인가?
- `없음`은 실제 업무값인가, NULL 표현인가?
- 상위영역이 없는 최상위 조직의 `parent_area_id` NULL은 정상인가?
- 필수 컬럼이 NULL이면 삭제할지 격리할지?

### 추천 정책

- Bronze: 원천값 그대로 보존
- Silver: 승인된 NULL 표현만 실제 NULL로 변환
- 필수 컬럼 NULL: Quarantine
- 선택 컬럼 NULL: 허용
- `미정`, `UNKNOWN` 같은 임의 대체값 사용 금지

## 5. 직원·업무영역 코드 논의

### 5.1 직원 ID

원천 예:

```text
emp000038
EMP000038
emp_000038
```

추천 표준:

```text
EMP000038
```

추천 규칙:

- 영문을 대문자로 변환
- 밑줄, 하이픈, 공백 제거
- `EMP` + 숫자 6자리

### 5.2 업무영역 ID

원천 예:

```text
biz_26652
BIZ11608
BIZ_00170
```

추천 표준:

```text
BIZ26652
BIZ11608
BIZ00170
```

추천 규칙:

- 영문을 대문자로 변환
- 밑줄, 하이픈, 공백 제거
- `BIZ` + 숫자 5자리

### 결정할 질문

- 자릿수가 부족하면 앞에 0을 붙일 것인가?
- 자릿수가 초과하면 오류로 볼 것인가?
- 접두사가 없는 숫자만 들어오면 `EMP`나 `BIZ`를 자동으로 붙일 것인가?

추천안은 값을 추측하거나 임의로 자릿수를 맞추지 않고 Quarantine으로 보내는 것이다.

## 6. 재직 상태 논의

현재 관찰값:

```text
Y
YES
사용
재직
N
NO
미사용
비활성
```

추천 매핑:

| 원천값 | Silver 값 | 처리 |
|---|---:|---|
| `Y`, `YES`, `사용`, `재직` | `true` | 정상 변환 |
| `N`, `NO`, `미사용`, `비활성` | `false` | 정상 변환 |
| 빈 값 | NULL | Quarantine |
| 알 수 없는 값 | NULL | Quarantine |

### 가장 중요한 질문

> `N` 또는 `false`가 정말 퇴직을 의미하는가?

현재는 확정되지 않았으므로 다음처럼 구분한다.

```text
false = 비활성
false ≠ 반드시 퇴직
```

퇴직 판정은 별도의 인사 업무 규칙이 확정될 때까지 TBD로 둔다.

## 7. 조직 레벨 논의

현재 관찰값:

```text
TOP
TOP_LEVEL
top_level
최상위
1
```

추천 표준값:

```text
TOP
```

### 꼭 확인할 질문

- 숫자 `1`이 항상 최상위를 의미하는가?
- 향후 `DIVISION`, `DEPARTMENT`, `TEAM` 같은 하위 레벨이 생기는가?
- `parent_area_id = top_area_id` 관계가 항상 맞는가?

검증하지 못한 관계는 확정 규칙으로 만들지 않고 TBD로 둔다.

## 8. 날짜 처리 논의

현재 날짜가 여러 형태로 섞여 있다.

```text
2021-12-01T05:30:46
2019-11-04 00:52:02.0
2018/03/085:41:19
2017.04.2104:38:58
2.02E+13
```

추천 Silver 형식:

```text
2021-12-01T05:30:46+09:00
```

### 팀에서 결정할 내용

- 기준 시간대: `Asia/Seoul`
- 출력 형식: ISO 8601
- 허용할 입력 포맷
- 미래 입사일을 오류로 처리할지
- 지수 표기 날짜를 자동 복구할지

### 추천 정책

- 명확한 날짜 형식만 자동 변환
- 지수 표기처럼 애매한 값은 추측하지 않고 Quarantine
- 변환 실패 원천은 Bronze에서 확인할 수 있게 유지
- `REG_DT` 충돌은 기준 원본 확정 전까지 변경 금지

## 9. 문자열 처리 논의

추천 기본 규칙:

- 양끝 공백 제거
- 전각 공백을 일반 공백으로 변환
- 연속 공백을 한 칸으로 정리
- 유니코드를 NFC로 통일
- 탭을 공백으로 바꾸고 보정 로그 기록

### 주의할 점

```text
"분 석팀"
```

이 값을 자동으로 `분석팀`으로 바꾸는 것은 위험하다. 내부 공백은 실제 명칭일 가능성이 있으므로 자동 삭제하지 않고 검토 대상으로 표시하는 것이 좋다.

## 10. Silver 테이블 분리 논의

추천 Silver 테이블:

```text
silver_employee
silver_area
silver_parent_area
silver_top_area_detail
silver_record_lineage
quarantine_records
```

| 테이블 | 역할 |
|---|---|
| `silver_employee` | 직원·관리자 정보 |
| `silver_area` | 업무영역과 담당 관리자 |
| `silver_parent_area` | 상위영역 |
| `silver_top_area_detail` | 최상위영역 상세 |
| `silver_record_lineage` | Silver 결과와 Bronze 원천 연결 |
| `quarantine_records` | 변환·검증 실패 데이터 |

### 결정할 질문

- 동일 직원이 여러 행에 있으면 어떤 행을 기준으로 중복 제거할지
- 이름은 같고 ID가 다른 직원을 같은 사람으로 볼지
- 하나의 관리자가 여러 업무영역을 담당할 수 있는지
- 상위영역과 최상위영역을 정말 별도 테이블로 유지할지

ID가 다르면 이름이 같아도 자동으로 병합하지 않는 것을 추천한다.

## 11. 오류 처리 논의

오류별 처리 기준을 팀에서 합의한다.

| 오류 | 추천 처리 |
|---|---|
| 필수값 NULL | Quarantine |
| 직원·업무영역 ID 형식 오류 | Quarantine |
| 상태값 미매핑 | Quarantine |
| 날짜 파싱 실패 | Quarantine |
| PK 중복 | 원인 확인 후 실행 실패 또는 격리 |
| FK 미매칭 | Quarantine |
| 파일 체크섬 불일치 | 실행 중단 |
| `REG_DT` 충돌 | 원본 보존·경고 |
| 내부 공백 의심 | 경고·검토 |
| RAW_DB 복원율 95% 미만 | 인수 실패 |

> 오류가 발생하면 데이터를 삭제하는 방식은 선택하지 않는다. 오류 데이터도 Quarantine에 남겨야 원인 확인과 복구가 가능하다.

## 12. 성공 기준 논의

Silver 완료 기준:

- RAW_DB 복원율 95% 이상
- Bronze 원본 무결성 100%
- PK 중복 0건
- 승인되지 않은 필수값 NULL 0건
- FK 고아 레코드 0건
- 승인되지 않은 도메인값 0건
- 날짜 파싱 실패 0건
- 입력 건수 = 통과 건수 + 격리 건수
- 모든 Silver 결과가 Bronze 원천과 연결됨

이는 원천에 오류가 전혀 없다는 뜻이 아니다. 오류를 정상 데이터에 섞지 않고 모두 식별하고 격리했다는 의미다.
