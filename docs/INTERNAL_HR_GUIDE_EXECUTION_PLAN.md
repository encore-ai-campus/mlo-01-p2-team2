# 내부 인사 요청 검토 가이드 실행계획

- 문서 상태: `Implementation In Progress`
- 기준일: `2026-08-27`
- 구현 상태: `Gate 0 승인 완료 — Gate 1 데이터 연결 대기`
- 대상 제품: 사내 Django 기반 인사 요청 내부대체 가능성 검토 보조 도구
- 데이터 기준: 현재 `MANAGER–AREA–PARENT_AREA–TOP_AREA_DETAIL` ERD
- 업무 정본: 기존 인사 요청서와 기존 인사 의사결정 프로세스

## 1. 목표와 비목표

### 목표

- 퇴직 대상 관리자의 현재 담당 업무영역을 확인한다.
- 동일 업무영역을 담당하는 재직 관리자를 내부 검토 대상으로 찾는다.
- 부서·직위·근속과 데이터 누락 여부를 중립적인 검토 근거로 표시한다.
- 팀 관리자와 HR 담당자의 인사 요청 검토 시간을 줄인다.
- 최종 인사 판단은 기존 인사 프로세스에서 HR 담당자가 수행한다.

### 비목표

- 후보 자동 선정 또는 Top-1 추천
- 인사 요청 자동 승인·반려
- 신규채용 필요·불필요 자동 결정
- 업무가 실제 수행 중인지에 대한 확정 판정
- 신규 업무 이력·후보 결과·인수인계·채용 케이스 테이블 추가
- 물리적 반정규화 테이블 추가
- 기존 인사 요청서와 최종 의사결정 이력의 복제

## 2. 운영 원칙

1. `is_active=true` 또는 고객이 승인한 재직 정본만 후보가 된다.
2. 퇴직 대상자는 후보에서 제외한다.
3. 업무영역 조인은 이름이 아닌 `parent_area_id/p_area_no`를 사용한다.
4. 부서·직위·근속은 기본적으로 탈락조건이 아니라 비교 근거다.
5. 결과는 `검토 가능`, `일부 검토 가능`, `근거 부족`, `판정 보류`로 제한한다.
6. 후보 존재는 인사 요청이 부당하다는 의미가 아니다.
7. 후보 부재는 신규채용이 필요하다는 자동 결론이 아니다.
8. 현재 스냅샷만 사용하므로 모든 결과에 `현재 등록정보 기준`을 표시한다.
9. 팀 관리자와 HR 담당자의 후보 개인정보 열람 범위를 분리한다.
10. 구현 변경은 승인된 범위와 테스트 완료기준 안에서만 수행한다.

## 4. 승인 게이트

### Gate 0 — 코딩 시작 승인

`2026-08-27` 사용자가 “자 지금부터 시작”이라고 명시하여 승인 완료했다. 아래 항목은 앞선 기획 대화에서 합의된 기준으로 동결했으며, 범위 변경은 다시 사용자 승인을 받는다.

승인된 기준은 다음과 같다.

- 제품 범위와 비범위
- `p_area_no`와 `p_area_nm`의 사용 의미
- 재직·퇴직 상태의 정본
- 후보 포함조건과 부서·직위·근속 표시방식
- 유사 직위 정의 또는 MVP 제외 결정
- 팀 관리자와 HR의 필드별 열람범위
- 기존 인사 요청서 입력·결과 전달방식
- 현재값 충돌·NULL 처리정책
- 화면 결과 문구와 면책문구

### Gate 1 — 데이터 연결 승인

- canonical 현재값 테이블에 실사용 데이터가 적재됨
- Manager/Area PK 중복 0건
- Area–Manager, Area–Parent FK 위반 0건
- Parent–Top 동일 키 관계가 승인된 규칙과 일치
- 관리자 현재 프로필 충돌이 0건이거나 경고·제외정책 적용
- 후보 SQL 기준값과 Django 조회 결과를 대사할 수 있음

### Gate 2 — 기능 시연 승인

상세 시나리오는 `docs/INTERNAL_HR_GUIDE_UAT.md`에 `PASS / FAIL / BLOCKED`로 기록한다.

- 팀 관리자·HR 화면의 정보노출 차이를 확인함
- 팀 관리자의 요청 대상 소유권을 기존 인사시스템 또는 SSO 정보로 제한함
- 복수 담당영역, 후보 없음, 일부 커버, 데이터 누락 시나리오를 통과함
- 후보별 근거가 설명 가능함
- 자동 인사결정으로 오인할 표현이 없음

### Gate 3 — 내부 운영 배포 승인

- HR UAT 승인
- 권한·PII·로그 검증 통과
- 운영 설정과 Secret 분리
- SQL 대사 통과
- 백업·롤백·Smoke Test 통과
- 파일럿 중단조건과 책임자 확정

## 6. 환경 준비 기준

### 2026-08-27 현재 확인된 상태

- 현재 브랜치는 `gold-implement`이며 구현 변경분은 아직 커밋하지 않았다.
- 손상된 기존 `django/.venv`를 재생성하고 `requirements.txt` 설치를 검증했다.
- `default` RDB와 기존 적재기 호환용 `sqlite3` 별칭, Mongo Router를 구성했다.
- 운영 Secret·DEBUG·Hosts·HTTPS 쿠키·HSTS 설정을 환경변수로 분리했다.
- migration graph는 테스트 DB와 운영 DB 복사본에서 정상 적용됐고, 복사본의 기존 19,621행·FK·무결성이 보존되며 SQLite에 Bronze 테이블이 생기지 않음을 확인했다.
- 실제 `db.sqlite3`는 외부 프로세스 잠금 때문에 migration을 적용하지 않았고 원본 상태를 보존했다.
- canonical Silver 4개 테이블은 각 1건, 재직 1건, 퇴직 0건이며 유일한 직원도 충돌/프로필 보류 대상이어서 Gate 1을 통과하지 못한다.
- 역할별 로그인·입력·팀 요약·HR 상세 화면과 판정 서비스를 구현했다.

## 10. 승인되어 구현에 반영된 결정

1. 동일 업무는 `p_area_no`로 조인하고 `p_area_nm`은 표시한다.
2. 부서·직위·근속은 제외점수가 아니라 비교 근거와 안정적 정렬에 사용한다.
3. 유사 직위 매핑은 MVP에서 제외한다.
4. 팀 관리자는 후보 실명·ID·부서·직위·근속 없이 수와 업무영역 요약만 본다.
5. HR은 검토 목적에 한해 이름·부서·직위·근속·일치 근거를 본다.
6. 결과는 화면에서만 확인하며 PDF/CSV·결과 저장·기존 시스템 자동연계는 제외한다.
7. 현재값 충돌·관계 누락은 `판정 보류`로 처리한다.
8. Gate 0 최종 승인자는 사용자 본인이다.

## 11. Gate 2 전 남은 정책 결정

1. 현재 ERD에는 Django 사용자와 조직·인사요청 대상의 소유권 관계가 없다. 팀 관리자의 자유 입력을 허용하지 않으려면 기존 인사시스템 요청 ID 또는 SSO 조직 claim 중 어느 것을 권한 정본으로 사용할지 결정해야 한다.
2. 미래 입사일인 재직 관리자는 현재 `근속 산정 불가` 경고와 함께 확인 대상으로 남긴다. 데이터오너가 잘못된 날짜로 규정하면 보류 정책으로 변경한다.
3. `DATE_CONFLICT`는 현재 upstream 표준계약에 정의된 유일한 blocking 충돌 코드다. 새 충돌 코드가 추가되면 서비스의 blocking 집합과 테스트를 함께 갱신한다.
4. `TOP_AREA_DETAIL`은 이번 판정 쿼리에 사용하지 않는다. 전체 RDB 정본 무결성 검사는 유지하되 기능 최소 준비도와 분리한다.

## 12. 변경관리

- Gate 0 완료 이후에도 범위·권한·판정 규칙을 바꾸는 구현은 사용자 재승인을 받는다.
- 승인된 업무규칙 변경은 영향 태스크와 테스트를 함께 갱신한다.
- 하위 에이전트는 각각 사업·기술 관점에서 계획과 결과를 독립 검토한다.
- 주 에이전트는 두 결과의 충돌을 근거와 함께 사용자에게 보고한다.
- 구현 단계에서도 코드 변경 전 관련 태스크 ID와 완료기준을 명시한다.
